01 / UNDERSTANDAGENTIC SDLC 08

概念與工作方法

dev-workflow-tdd：從需求到可 Review 的 PR

dev-workflow-tdd 用七個 Step，把需求釐清、實作、驗證與交付接在一起。實作時就沿這張地圖追蹤進度。

Step做什麼重點
1接收任務模糊需求、Spec 或 Azure DevOps Work Item
2grill-with-docs讀既有知識，一問一答陪你把 Spec 補完整：需求、Domain 知識與決策
3開新的 Branch可選開 Worktree：平行任務各用自己的目錄；不開就在原目錄開 Branch
4TDD 開發Red → Green → Refactor
5驗證與 Code Review測試、瀏覽器操作、整合驗證與 diff Review
6Commit提交已驗證的程式、測試與相關文件
7自動開 PR附上修改摘要、驗證結果與待注意事項

Step 5–7 的 Code Review、Commit、開 PR，都能換成你們團隊的規則與模板。dev-workflow-tdd 是底稿，最後一段就用它寫出你們自己的 Workflow Skill。

兩個 Task-level Skill：修弱點與寫文章

Agent 在跑 TDD，人不用盯著。趁這段時間，把同一套「給任務 → 確認邊界 → 驗收證據」用在日常工作。換的是工作，委派方式相同。

實跑 · AZURE-FIX-SECURITY-ISSUE

修弱點

  1. 讀 CI Build 結果給 Build URL，找出弱點、套件位置與受影響範圍
  2. 最小安全修補確認版本與相容性，只改必要範圍
  3. 驗證與交付重跑掃描、測試與 Build，說明殘餘風險
介紹用途 · TKMS-ARTICLE

寫文章

把素材整理成文章、填進 TKMS 草稿；人看過再發。

延伸 · ORACLE MCP 可選讓 Agent 直接用資料庫驗證
  • 驗證 SQL：Agent 寫完查詢，直接在測試資料上跑，確認語法和結果對不對
  • 建立測試資料：依情境在測試環境產生資料，不用手動準備（今天不示範）
  • 確保程式正確：用資料庫裡的實際結果，核對程式的輸出

Task-level Skill 的共同點：範圍小、輸入清楚、完成條件明確。

05 / NEXTAGENTIC SDLC 18

收尾

從盯著一個 Agent，到協調兩個任務

開場問的三個擔心：講不清楚、會打架、來不及 Review，今天各給了一個做法。Step 1→2 的改變，是你開始負責交代、協調、驗收與交付；兩個 Agent 是練習，可靠交付才是判斷依據。

  1. 交代清楚，再分工

    TSMC Week 從 Work Item 開始、匯出對話直接給 Spec；各開一個 Session 與 Worktree，各自問到可驗收。

  2. 看證據，處理例外

    讓 Agent 自己推進 TDD；人處理決策、檢查畫面與下載內容，確認未驗證項目。

  3. 兩份成果，各自交付

    各自重跑檢查、附上驗證結果，各開一份可 Review 的 PR。同樣的方法，也能用在修弱點、寫文章與團隊流程。

05 / NEXTAGENTIC SDLC 20

收尾

我們離 Step 3 還差什麼

Step 3 的門檻是信任：公司願不願意、工程師敢不敢讓 Agent 合併。信任不是談出來的，是測試環境、Domain 知識、Agent 的環境一項一項補出來的。

哪一層為什麼卡住怎麼解決
公司的態度公司願不願意讓 Agent 自動合併 PR，還沒有答案先挑一類低風險變更試行（例如測試、文件、內部工具），講好出問題就 revert、隔天抽查，用試行結果去談
工程師的把握敢不敢放手，取決於測不測得到測得到的才放手；抽查發現問題就改環境。要和下一列的測試環境一起看
測試環境還不完整，有些問題要到接近 Production 的環境才測得出來；測不到，工程師就沒把握放手按變更類型分：測得到的先放手，碰到整合與權限的照舊人審
Domain 知識Reviewer 在看的業務規則，還有一部分沒寫下來grill-with-docs：問清楚就寫進 GLOSSARY.md 與 ADR；驗收條件由人確認，測試從它推出來
Agent 的環境自動驗證還蓋不到 Reviewer 會挑的每一種問題用 /retro 回顧 session 和 PR，找出要優化的 Skill、要串的 MCP、要加的 lint 規則；改好環境，下次不用人看
Agent 怎麼開工每件事都要人開 Session、下 Prompt，Agent 不會自己開始先挑重複的維護工作（例如修弱點、清 lint 警告），用排程或事件叫醒 Agent；結果一樣走驗證、隔天抽查

CI 全綠，不代表可以合併

AI 寫的測試常見三種騙法；自動化檢查過了，還是要看測試到底驗了什麼。

套套邏輯

程式寫 LIMIT = 280，測試就寫 expect(LIMIT).toBe(280)。只是把實作再抄一次，沒有驗到行為。

對結構過敏

不渲染畫面，直接讀原始碼檔案比對字串先後。程式一重排就失敗，功能壞了卻不一定抓得到。

不可能失敗

把 AudioContext 這類 API 整個 mock 掉，正式環境才會出現的錯誤，測試永遠測不到。

解法從架構下手：用 Deep Module 把複雜實作藏在簡單介面後面，並要求 Agent 只從介面測。

已經有 AI Review，下一步是放進團隊規範

公司有 AI Reviewer，dev-workflow-tdd 也有 Code Review 環節。Matt Pocock 的提醒是：通用的 Reviewer 不是太廣而一直誤報，就是太窄而不適用；要真的有用，得累積自己團隊的規範。

IMPLEMENT AGENT · 已經滿載
  • 探索：找出要改哪裡
  • 實作：修改檔案
  • 除錯：跑驗證、修到通過

再塞 coding standards，三件事都做得更差。

CODE REVIEW 環節 · 還很空
  • 拿到 diff，只需補看周邊脈絡
  • 不用實作，也不用除錯
  • 有自己的 context，逐條對照規範

規範交給它，效果好得多。

規範放 coding-standards.md

給 dev-workflow-tdd 的 Code Review 環節讀，不放進 AGENTS.md，免得搶走實作的注意力。那些沒人讀的內部規範文件，終於有地方用。

能修的直接 commit

Code Review 環節找到問題就修，有疑問才留 comment。人看到的是修好的成果，而不是一串要自己判斷的意見。

同樣的 Review comment 不寫第二次：人工 Review 發現的問題，就寫進 coding-standards.md、lint 或 Skill，也就是我們說的「改環境」。用 /retro 定期回顧 session 和 PR，找出該改哪裡。

附錄 · Review 瓶頸

不是每個 PR 都一樣危險：單向門與雙向門

大部分 PR 是雙向門，隨時能 revert；要細審的是回不去的、以及爆炸半徑大的——一行設定也可能寄信給六萬人。讓 Agent 在 PR 描述裡先標出來，人就知道力氣該花在哪。

雙向門 · 可以輕審

走錯了可以退回來：合併後隨時能 revert，影響也能完全收回。

  • 內部重構、UI 文字調整
  • 有測試覆蓋的一般功能

看摘要與驗證證據即可。

單向門 · 一定要細審

走過去就回不來：就算 revert 程式，資料已刪、信已寄出，影響收不回。

  • 資料 migration、刪除資料
  • 對外寄信、發通知
  • 權限、整合與上線設定

逐行看，必要時找人一起看。

## Merge 風險
- 可逆性：雙向門（可直接 revert）
- 爆炸半徑：只影響報表頁的匯出
- 建議 Review 深度：看摘要與驗證證據
一起討論
  • 我們的測試環境不完整，哪些變更其實比看起來更「單向」？
  • 你們平常怎麼判斷一個 PR 要看多細？
  • 哪一類 PR，你願意先只看摘要？

單向門每個都要審；雙向門，不用每個都看。

參考：Matt Pocock〈Fixing the PR Bottleneck〉，AI Engineer 大會演講，依內容整理並對照我們的流程，非講者原圖；單向門／雙向門的分類來自 Amazon。
